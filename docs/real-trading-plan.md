# 正式環境（真錢）交易：規劃與全流程檢視

狀態：**規劃草案，尚未實作、尚未經你確認**。範圍：先打通 Binance 與 Bybit（OKX 不含）。日期：2026-10-15。
目的：列出要調整的項目、非常顯著的切換提醒（避免用錯環境）、並把整條執行流程再過一遍。

## 1. 現況（都已對照程式碼確認）

| 面向 | 現況 | 對正式環境的意義 |
|---|---|---|
| 執行模式 | 只有 `SIMULATION`、`EXCHANGE_DEMO`；規格明寫設為 `LIVE` 會驗證失敗（`core/src/risk.rs`、risk-config spec） | 需要新增第三個模式，這是刻意要改的安全設計 |
| 簽名請求的主機 | 只有編譯期寫死的 demo／testnet 主機（`app/src/exchange/signed/endpoints.rs`：`testnet.binancefuture.com`、`demo-fapi.binance.com`、`api-demo.bybit.com`）；沒有任何建構子接受外部網址 | 簽名請求目前**不可能**送到正式主機；要送就必須明確新增 |
| 靜態檢查 | `app/src/exchange/static_checks.rs` 掃描原始碼：正式主機（`fapi.binance.com`、`api.bybit.com`）只能出現在公開（不簽名）的客戶端 | 這條保護網會擋住任何 live 程式碼；要改成「只允許出現在一個指定檔案」，不是拿掉 |
| 金鑰 | Keychain 以 `{交易所}:api_key`／`api_secret` 儲存，**每個交易所只有一組**（`app/src/store/secrets.rs`） | demo 與 live 金鑰無法並存，也無法區分；有用錯金鑰的風險 |
| 配對的環境標記 | 只有布林值 `simulated`（`PairEnvelope`）；引擎已有 `executor_mismatch` 防止配對被另一個環境的執行器處理 | 要從兩種環境擴充為三種（模擬／demo／live） |
| 資料庫 | 單一檔案 `funding.db`，事件、配對、設定全在裡面 | demo 與 live 的紀錄會混在一起；分析與稽核會出錯 |
| 掃幣資料 | 本來就用正式環境公開資料 | 好處：live 時掃幣與下單終於是同一個市場（001 的 Binance demo 落差消失） |
| 下單 | 只有市價單（`MARKET`）＋`reduceOnly` 平倉；送單前有價格漂移檢查（對基準價），沒有成交滑價上限 | live 的滑價是真錢損失（10-14／15 實單價差損益合計 −0.5 至 −4.5 USDT／筆） |
| 持倉模式 | 已有檢查（Binance `positionSide/dual`、Bybit `positionIdx`）：單向才可交易 | 已有基礎；但**保證金模式（全倉／逐倉）沒有檢查** |
| 金額上限 | 每腿名目是常數 1,000 USDT（`SCAN_NOTIONAL_USDT`）；風控只有 `max_concurrent_pairs`、`max_leverage` 等；OKX 才有絕對金額上限 | live 沒有「單筆金額硬上限」「單日虧損上限」「總曝險上限」 |
| 緊急停止 | kill switch：阻擋「新開倉」，不強制平倉；已有平倉不受影響 | live 要補「自動解除武裝」（見 4.4） |
| 帳戶／槓桿／資金費流水 | 全部走 demo 主機的簽名客戶端 | 每一條都要有 live 版本與環境參數 |
| 實際經驗（10-14／15） | 費率設定偏低、Bybit 流水曾延遲 3 小時、下單回應 1.3～2.4 秒、單邊結算進場（已用同步結算規則擋掉） | 這些在 live 都是真錢問題，要先在 demo 觀察穩定 |

## 2. 設計原則

1. **失敗即封閉**：任何環境不確定、金鑰不符、預檢失敗，一律不下單。
2. **進入 live 要「武裝」，不是切換選項**：每次啟動 app 都預設模擬；live 不被記住。
3. **環境是資料，不是旗標**：每個配對、事件、訂單意圖都帶 `venue`（`SIM`／`DEMO`／`LIVE`），所有簽名請求的主機由 `venue` 決定，沒有第二個入口。
4. **demo 與 live 的資料完全分開**：不同的資料庫檔案、不同的金鑰、不同的事件前綴。
5. **硬上限在引擎，不在畫面**：畫面可以被繞過，引擎不行。
6. **先唯讀、再影子、再小額、最後放大**：每一階段有明確的通過條件。

| 4 | `live-mode-warnings` | 非常顯著的視覺與流程提醒（見 4.3）；每筆配對／訂單／事件的環境徽章；macOS 通知 | 1 |

註：上表提到的交易所端點（金鑰權限、手續費率、交易狀態）是依我對官方文件的記憶列出，**實作前每一個都要對照官方文件與實測確認**，尤其是 Binance 判斷提領權限的方式（期貨主機的端點可能讀不到，需用現貨 SAPI 主機，那會新增一個要放行的主機）。

## 4. 重點設計

### 4.1 預檢清單（全部綠燈才能武裝）
- 兩所 live 金鑰都存在，且指紋（金鑰末 4 碼）顯示給使用者核對；金鑰不是 demo 金鑰（用 live 主機做唯讀呼叫驗證）。
- 金鑰權限：可交易、**提領權限關閉**、有 IP 白名單（交易所端設定，app 只讀取並提示）。
- 兩所時鐘校時成功（偏移在容許範圍）。
- 持倉模式為單向；保證金模式符合預期（全倉或逐倉，由你決定一種）。
- 該帳戶在要交易的幣種上**沒有既有部位或掛單**（既有 `ExistingExposure` 檢查沿用）。
- 可用保證金 ≥ 硬上限所需的保證金與緩衝。
- 實際手續費率已讀取，且與風控設定的差距在容許範圍內（否則警告）。
- 硬上限四個欄位都已填寫；kill switch 為關閉；資料庫為 live 專用檔案。

### 4.2 武裝流程（不是下拉選單）
1. 在風控設定頁選 `EXCHANGE_LIVE` 只會「開始武裝」，不會切換。
2. 跳出全螢幕確認：列出兩所帳戶別名／金鑰指紋、可用餘額、四個硬上限、預檢結果、「這會動用真錢」。
3. 使用者必須**手動輸入指定字串**（例如 `我了解這是真錢 LIVE`），按鈕才可按；輸入框不可貼上（降低誤觸）。
4. 武裝成功後只在這次執行有效：**app 重啟一律回到模擬**，live 不會被記住。
5. 觸發模式預設 `MANUAL`（人工勾選與觸發）；要改成 `AUTO` 需要第二次獨立確認，並建議在小額階段通過後才開放。

### 4.3 非常顯著的提醒（避免用錯環境）
- **整個視窗頂端固定一條不可關閉的紅色橫幅**：`⚠ LIVE 真錢 · Binance + Bybit 正式環境 · 今日損益 −x USDT／上限 y`；每一頁都有。demo 為琥珀色橫幅 `DEMO（模擬帳戶，不涉及真錢）`，模擬為灰色 `模擬`。
- 視窗標題列文字也帶環境（`[LIVE]`），macOS Dock 圖示名稱／視窗標題可辨識。
- **整個 app 的強調色隨環境改變**（live 為紅色系邊框與按鈕），而且**文字一定寫出環境名稱**，不靠顏色單獨區分。
- 每一個「加入交易單」「進場」「平倉」「立即平倉」的確認對話框重複顯示環境與金額；live 時按鈕文字為「以真錢下單」。
- 每個配對卡、交易單列、訂單紀錄、系統日誌事件都帶 `LIVE`／`DEMO`／`SIM` 徽章。
- 武裝成功、第一筆 live 單送出、自動解除武裝時，各發一則 macOS 系統通知，並在畫面留下不可忽略的記錄。
- 金鑰用錯的情況：Binance `-2015`、Bybit `10003/10004` 等認證錯誤會被翻成明確訊息「這組金鑰不屬於 LIVE 環境」，並自動解除武裝。

### 4.4 自動解除武裝（回到模擬、不再開新倉，既有部位照常平倉）
- 單日損益達 `live_max_daily_loss_usdt`；任何 `PARTIAL_FAILURE`／`IMBALANCED`／`UNRESOLVED`；kill switch 開啟；連續下單失敗；時鐘失同步；認證錯誤；損益與交易所流水對不上；預檢中途變紅。
- 解除武裝時畫面出現不可忽略的紅色說明，並寫事件。

## 5. 全流程檢視（每一步在 live 的風險與要調整的）

| 步驟 | 現況 | live 要注意／調整 |
|---|---|---|
| 1 掃幣 | 正式環境公開資料；Bybit WebSocket 覆蓋；同步結算規則 | 已對齊；live 時不再有 demo 落差。WebSocket 失效退回 REST 是安全的（較慢）。 |
| 2 達標 | Net Edge、成交量、同步結算、`min_expected_net_pnl_pct` | 手續費設定必須用**實際讀到的費率**（10-14 的 0.61 預估 vs 實際 1.9～2.1）；滑價預留（0.005%／腿）與實測不符，需用 live 小額資料重新校準。 |
| 3 加入交易單 | 手動或自動（距結算 ≥ 90 秒） | live 預設只能手動；每次加入的確認要顯示環境與金額。 |
| 4 進場前檢查（T−10 秒） | 10 項檢查，重抓最新資料 | 新增「硬上限檢查」與「環境一致性（`venue` 與金鑰與主機）」；保證金模式檢查；單筆最大滑價。 |
| 5 下單 | 兩腿同時、市價單、單向模式 | **市價單的滑價是真錢**：改為「有價格上限的 IOC 限價單」或至少事前估算滑價並設上限；觸發到回應 1.3～2.4 秒（10-15 批）需要在 live 小額觀察；Binance 每秒下單權重、Bybit 限頻要納入限流。 |
| 6 成交監控 | 15 秒逾時；一腿成交另一腿未成交 → `PARTIAL_FAILURE` 交人工 | live 的單腿暴露是方向性風險：要有明確的**人工處理指引**與通知；考慮把逾時縮短。 |
| 7 持倉 | 約 25 秒；單腿提早平倉（T+5～T+15，預設 0.3%） | 提早平倉會留下單邊曝險，live 小額階段建議先設為 0（停用）再逐步開；價差標籤僅供參考。 |
| 8 平倉（T+15） | 兩腿 reduce-only 市價單 | 同第 5 項的滑價；平倉失敗要通知；重啟後 live 對帳必須以交易所實際持倉為準。 |
| 9 資金費流水 | demo 主機的簽名客戶端；Bybit 流水曾延遲 3 小時；Binance 約 2.5 分鐘 | live 版本的流水客戶端；延遲期間損益顯示 `INCOMPLETE`；未收到流水前**不得**把該筆當作最終獲利；與預期（T−10 費率推算）對帳，差距過大就警告。 |
| 10 損益與結案 | PnL 記錄、對帳 | live 損益要和交易所帳戶餘額變化定期核對（每日），差異超過門檻就自動解除武裝。 |
| 11 重啟與當機 | 持倉中重啟：不重送單、以實際持倉對帳；提早平倉的均價遺失則不提早平倉 | live 重啟後要重新預檢，且重啟不會自動武裝。 |
| 12 帳務與稽核 | 事件為只增不改 | live 事件帶 `venue`；資料庫分開；每日匯出報表（可沿用 `issue/tools/trade_table.py` 的格式）。 |

## 6. 上線階段與通過條件

| 階段 | 內容 | 通過條件 |
|---|---|---|
| 0 唯讀 | 只讀取 live 帳戶：餘額、持倉、費率、金鑰權限、資金費流水；**不下單** | 預檢全綠；讀到的實際手續費率與設定一致；不會觸發任何簽名的寫入請求（用測試證明） |
| 1 影子 | live 掃幣與進場前檢查照跑，但只記錄「若下單會怎樣」 | 連續數個結算點，預期損益與事後以公開資料重算一致 |
| 2 極小額人工 | 每腿 20～50 USDT、1 個配對、`MANUAL` 觸發、提早平倉停用 | 單筆實際損益、手續費、滑價、資金費與預期對得上；無 `PARTIAL_FAILURE`；Bybit／Binance 流水與帳戶餘額一致 |
| 3 小額自動 | 小額、`AUTO`、單一配對上限 | 多個結算點無異常；自動解除武裝經演練可正常運作 |
| 4 放大 | 逐步提高硬上限 | 每次提高前回顧一次損益、滑價、延遲資料 |

## 7. 需要你決定的事（規劃會依答案調整）

1. 硬上限的起始值（階段 2 的每腿金額、同時配對數、單日虧損上限）。
2. 保證金模式要用全倉還是逐倉，Bybit 是否使用統一帳戶（UTA，目前程式假設）。
3. 市價單滑價的處理方式：維持市價單加事前上限檢查，或改為有價格上限的 IOC 限價單（較安全，但可能成交不完整）。
4. 要不要把 live 的資料庫與 demo 完全分開（我建議要）。
