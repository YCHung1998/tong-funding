## Context

- 兩腿共同數量由 core `matched_quantity` 決定（`matched-leg-quantity`）。
- 行情輪詢每 10 秒（`MARKET_POLL_MS`）：Binance `premiumIndex`（另有 WebSocket mark price）、Bybit `/v5/market/tickers`、OKX tickers / mark-price。Bybit 與 OKX 的 tickers 已含 bid1 / ask1 的價與量；Binance 的 `premiumIndex` 沒有。
- 送單前檢查（`engine/node0.rs`）使用送單前剛抓的價格與費率，`margin_needed = notional ÷ leverage`，未計手續費。
- 手續費率：風控設定 `taker_fee_pct` 為必填，風控頁標記為「事實值」（依帳戶等級實填）。

## Goals / Non-Goals

**Goals:** 在固定數量下顯示實際成本與手續費並滾動更新；保證金檢查計入手續費；不拖慢下單。

**Non-Goals（列為後續 change）：**
- 交易所實際槓桿與設定槓桿不一致的檢查（程式不設定交易所槓桿，實際所需保證金可能更高）。
- 同時進入送單前檢查的多組配對互相保留保證金（目前各自看到完整餘額；模擬與真實配對也共用同一 demo 餘額）。
- 以 WebSocket 推送最佳一檔（`bookTicker` / `orderbook.1`）。
- 呼叫交易所手續費率 API。

## 送單速度影響分析（使用者 2026-10-06 要求保存於此供日後查閱）

結論：依本設計實作，對下單速度的影響接近 0；最差情況是多一次「並行」的網路往返，不會累加。

1. **真正影響速度的只有關鍵路徑**（決定送單 → 送出）：抓兩腿最新價格與費率、可用保證金，再做本地檢查。時間幾乎都是網路往返（每次約 50–500 ms）；本地 Decimal 計算是微秒級，可忽略。
2. **手續費率不放在關鍵路徑**：帳戶 taker 費率取決於 VIP 等級，幾乎不變。使用風控設定的 `taker_fee_pct`（或日後改為啟動時抓一次並定期更新快取）；「數量 × 價格 × 費率」只是乘法，成本為 0。
3. **最佳一檔多半不需要多打 API**：Bybit `/v5/market/tickers` 與 OKX tickers 本來就附 bid1 / ask1 價量，同一個回應就有。Binance 需另抓 `bookTicker`（輕量），但與現有抓取同時發出，總延遲取兩者較慢者，不是相加；且它在背景輪詢中，不在送單路徑上。
4. **滾動顯示在背景**：交易單頁的預估成本由背景輪詢計算，畫面更新不擋下單。若要接近即時，可訂閱 Binance `bookTicker` 與 Bybit `orderbook.1` WebSocket（延遲最低，但要多管理連線），列為後續。
5. **取捨**：買一 / 賣一掛單量可能小於固定數量，實際成交價會比一檔差；顯示時比較「數量 ≤ 一檔掛單量」，不足就標示會吃到第二檔。只提示、不阻擋，不影響速度。

## Decisions

1. **最佳一檔放進行情快照**：與 funding 觀測同一輪取得、同一個資料時間，UI 與估算都從快照讀。
2. **成本估算為 core 純函式**：交易單頁與送單前檢查共用同一套公式，避免顯示與檢查不一致。
3. **送單前檢查用送單前最新價（非一檔價）計算所需保證金**：送單前已抓到的是最新價；為了不在關鍵路徑上加請求，不另抓一檔。一檔價只用於顯示的成本估算。
4. **平倉手續費只做顯示估算**：不計入開倉所需保證金（平倉時才發生），但列在總成本中讓使用者看到完整往返成本。

## Risks / Trade-offs

- [顯示用的一檔報價最多晚 10 秒] → 顯示資料時間；送單前檢查另以最新價與 `max_price_drift_pct` 把關。
- [Binance `bookTicker` 全市場請求增加權重] → 每 10 秒一次、權重低；限流時沿用既有退避，該所最佳一檔標示不可用。
- [所需保證金變大可能讓原本剛好通過的配對失敗] → 這是預期的保守行為；交易單頁會先顯示所需保證金，使用者可預見。
