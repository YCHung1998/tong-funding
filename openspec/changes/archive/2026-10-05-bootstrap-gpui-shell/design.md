## Goals / Non-Goals

**Goals**
- 驗證 GPUI 能撐起 8 頁的核心元件（表格、圖表、側邊欄、中英字型）。
- 定型 workspace 結構，使 `core` 的測試迴圈不必連結 GPUI。
- 建立集中的 theme 模組，之後各頁不再各自挑色。

**Non-Goals**
- 不做任何頁面的實際內容、資料或互動。
- 不接網路、資料庫、金鑰。
- 不處理 Windows / Linux。

## Decisions

**D1　兩個 crate：`core` + `app`。**
只保留「純邏輯與 GPUI 分開」這條真正有價值的邊界（抗辯中 simplifier 的結論）。
`exchange` / `store` / `engine` 先是 `app` 內的模組，之後有第二個呼叫者再拆。

**D2　theme 為 Rust 常數，不做執行期載入。**
單人工具不需要主題切換；常數可由編譯器檢查，且「theme 之外不得有色碼字面值」可用測試強制。

**D3　只打包 IBM Plex Mono，中文交給系統字型。**
Figma 以 IBM Plex Mono 為主（622 個節點）。授權已確認為 SIL OFL 1.1（讀取上游 `OFL.txt` 檔頭）。
原計畫同時打包 Noto Sans TC 作為中文後備字型，實測無效而放棄（見下節）；使用者於 2026-10-05 表示字型「可顯示即可」，不再深入。

**D4　`gpui-kit` 鎖定 `=0.7.1`。**
GPUI 生態變動快，v1 期間不跟隨升級。

**D5　效能預算（2026-10-05 由使用者確認，取代原本的 p95 ≤ 16.7 ms）：**
**(a) 掉幀率 ≤ 0.5%：幀間隔超過 1.5 × 當下 vsync 週期（以 p50 估計）算一次掉幀；間隔超過 250 ms 視為視窗被遮住或暫停，不算掉幀、另行回報；(b) 每幀 CPU 時間 < 一個 vsync 週期。**
理由：幀間隔被螢幕 vsync 鎖住（本機 60Hz 時 p50 恰為 16.67 ms），因此「p95 ≤ 一個 vsync 週期」是不可能穩定達成的硬體下限，且看不出餘裕；
Binance `!markPrice@arr` 約每秒推全市場一次，UI 端限頻到 2–10Hz 是 `engine-simulation` 的既定設計。
若未達標，緩解選項依序為：降低更新頻率 → 只重繪可見列 → 自繪表格。

## 文字對比度（使用者回饋，2026-10-05）

使用者回報表格 spike 的灰色文字看不清。兩個原因，皆已修正：
1. gpui-component 的元件預設為淺色主題（白底列），我們的近白文字在其上幾乎不可見；新增 `ui/component_theme.rs` 把色票套用到元件庫的深色主題。
2. Figma 的弱化文字色 `#586B80` 在我們的背景上對比度只有 2.94–3.48:1（WCAG 建議小字 ≥ 4.5:1）；改為 `#7A8CA2`，在四個背景上為 4.68–5.55:1。這是**刻意偏離 Figma** 的一處。

## 字型實測（task 2.4，2026-10-05）

做法：`app` 開一個字型檢查視窗，以 `screencapture` 截圖後用 PIL 逐像素比對；每次只改一個變因。

| 對照 | 結果（與基準比較） | 解讀 |
|---|---|---|
| 不註冊任何打包字型 | Latin 與中文列都不同 | `add_fonts` 有作用，打包的 Plex Mono 確實被使用 |
| 只不註冊 Noto（Plex 仍註冊） | 中文列**逐像素相同** | Noto 當後備字型時完全沒被用到，中文由系統字型繪製 |
| 把 Noto 設為主字型 | 中文列明顯不同 | Noto 檔案本身可載入，是 GPUI 的後備字型機制沒有解析到它 |

我猜原因是 macOS 的後備字型以名稱到系統登錄找，而 `add_fonts` 只註冊在 GPUI 內部，**這是推測，未驗證**。
Noto Sans TC 上游為 11.9 MB 可變字型（wght 100–900，預設 Thin）；實測子集化後每個字重約 4.9 MB，兩個字重約 9.7 MB。
現行做法：中文用系統字型，不打包 Noto。若日後要與 Figma 字體完全一致，可行方向（皆未實作）：以 CoreText 在行程範圍註冊字型使後備可見，或把中文片段另以 Noto 為主字型的文字區段繪製。
Figma 中的符號（◈ ▾ ☑ ⚠ ✕ ⏱）與 emoji（🟢 🔄 🚀 ✅ 💾）不在 Plex Mono 內，截圖顯示由系統字型後備繪製且可見；後續頁面也可改用 gpui-kit 內建圖示。

方法上的教訓：第一次 A/B 因視窗沒有置頂，截到別的應用程式，差異像素數剛好等於整個框而被我判為無效；`screencapture` 會截整個桌面，後續改為只截目標視窗。

## Risks / Trade-offs

- **`cargo build` 尚未在這台機器上實測。** 這是本 change 第一個 task，失敗則整個計畫要重新評估。
- **GPUI 在高頻更新下的重繪成本未知。** 由基準頁量測，不憑推論。
- **字型授權與打包大小。** Noto Sans TC 完整字集體積大，可能需要子集化；視實際大小決定。

## Open Questions

- 預算 16.7 ms 是否需要放寬（例如 33 ms / 30fps）：待量測後與使用者確認。

## 量測紀錄（task 4.1 / 4.2 / 4.3，2026-10-05）

環境：Apple M5 MacBook Air（Mac17,3）、16 GB、2560 × 1664 Retina；`cargo build --release`；每組執行 10 秒，捨棄前 30 幀暖機。
重現：`cargo build --release -p tong-funding && ./target/release/tong-funding --bench-table <hz> 10`（原始碼：`app/src/ui/bench.rs`、統計：`app/src/ui/frame_stats.rs`）。
刻意取最壞情況：每一幀都要求重繪（`request_animation_frame`），不論資料有沒有變；表格 528 列 × 8 欄、虛擬化。

| 機器 | 列數 | 更新頻率 | 幀數 | p50 (ms) | p95 (ms) | max (ms) |
|---|---|---|---|---|---|---|
| M5 / 60Hz | 528 | 1 Hz | 564 | 16.67 | 17.64 | 17.76 |
| M5 / 60Hz | 528 | 2 Hz | 567 | 16.67 | 17.65 | 17.76 |
| M5 / 60Hz | 528 | 10 Hz | 567 | 16.67 | 17.23 | 18.57 |

CPU（10.3 秒運行的行程總 CPU 時間，約 570 幀）：無資料更新的基準 3.06 s、10 Hz 更新 2.96 s、1 Hz 更新 2.97 s，
約為單核 29%、**每幀約 5 ms**；資料更新頻率在 1–10 Hz 範圍內沒有可測得的差異（成本來自逐幀重繪，不是資料更新）。

**判定（task 4.3）**
- 原預算（p95 ≤ 16.7 ms）字面上未達（17.2–17.7 ms），但那是 vsync 抖動造成的硬體下限，不是效能問題。使用者於 2026-10-05 同意改採 D5 的新預算。
- 新預算 (b)：每幀 CPU 約 5 ms < 16.67 ms，**達標**。
- 新預算 (a)：第一組量測（60Hz、無暫停）最大幀間隔 17.76–18.57 ms，沒有掉幀，**達標**；但第二組量測受系統狀態影響，見下節，**只能說「未發現應用程式造成的掉幀」，不能宣稱在所有電源狀態下達標**。
- 緩解措施（降頻、只重繪可見列、自繪表格）此時不需要。

**補充量測與限制（2026-10-05 晚）**
- 量測工具加上「掉幀」與「暫停」的區分（`frame_stats::drops` / `split_paused`，先寫測試再實作）：原本的程式只有 p50/p95/max，視窗被遮住時會出現 5 萬到 13 萬毫秒的幀而無從辨識。
- 第二組量測時機器為**電池供電且開啟低電量模式**（`pmset -g` 顯示 `lowpowermode 1`），螢幕更新率被系統降低：p50 變成約 33 ms（約 30Hz），p95 約 50 ms。
  以當下 p50 為基準，掉幀為 0–6 次 / 約 270 幀（0–1.9%），且多次重測的結果互相差異很大（同時 WindowServer 與其他應用程式也在運作），**這組數據不可靠，不拿來判定預算**。
- 這印證了使用者的判斷：存在由硬體與系統電源狀態決定的更新率下限，因此預算以「當下實際更新率」為基準，而不是固定的 16.7 ms。
- **建議（未做）**：接上電源、關閉低電量模式、桌面上沒有其他視窗遮擋時，重跑 `--bench-table 1|2|10 10` 各數次並記錄；量測表應增加「電源狀態」欄位。
- 限制：表格內容是 8 欄的合成文字，真實掃幣頁欄位更多、儲存格更複雜；以真實資料與真實更新頻率的重量測留給 `ui-readonly-pages` task 4.2。

**甜甜圈圖 spike（task 4.2）**：`PieChart`（`inner_radius` 70 / `outer_radius` 110）以 Figma 的 Binance 資產分布（USDT 16,200、BTC 3,010、ETH 1,490、合約 1,300）可正確繪製，
四個扇形比例與資料相符；未設定圖例與標籤，標籤樣式留待 `ui-readonly-pages`。執行：`./target/release/tong-funding --bench-donut`。
